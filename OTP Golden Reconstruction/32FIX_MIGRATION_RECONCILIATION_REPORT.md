**Scope:** Reconcile P0 hotfix migration `00198` (branch `hotfix/p0-security`, commit `2dd3c2d`) against local-main migrations `00198`–`00203` (commits `5325988`/`769813a`/`4db44c4`/`c23d6fc`/`d3e98a9`/`168409e`), both descending from `a1586c9`. ## 1. Executive Finding

**The migration-numbering collision is real and confirmed at the Git level** (§2): local main's own `00198`–`00203` and the P0 hotfix's separately-authored `00198` are two sibling commit chains off the same parent (`a1586c9`), not variants of one migration — the P0 file (9,905 lines) and local's six files (2,974 lines combined) were written independently and never reconciled.

**The Phase-0 artifact's overlap claim is directionally right but materially overstates its breadth.** P0 fully or near-fully duplicates local `00198` and roughly half of local `00199` (the admin-guard sweep and several named fixes). Against local `00201` and `00203`, however, P0 duplicates **exactly one object each** (`audit_events_delete`, and `guard_profile_privileges` respectively) — the other 2/3 of each of those files (`procurement_stage_events`/`support_tickets` scoping in `00201`; ops-metadata RLS and one-live-TDS enforcement in `00203`) is **100% independent of P0 and not gated by this collision at all**. Local `00200` and `00202` have **zero** P0 overlap and were correctly left out of the Phase-0 artifact's overlap list, but the practical consequence — that most of `32FIX_IMPLEMENTATION_ORDER.md`'s "must wait for reconciliation" list (§9) is broader than the evidence supports — was not previously stated. Of the 11 batch items spot-checked against the actual SQL, 6 were found to be incorrectly gated on this reconciliation decision.

**Exactly two genuine, named behavioral forks exist, both correctly requiring a product decision, neither resolvable by this report:**
- **Conflict A — `admin_bulk_delete_users` (§6):** P0 retains a caller-selectable hard-delete path (cascading, irreversible); local converts the function to soft-delete-only. This is a real product/security policy choice.
- **Conflict B — synthetic/demo-quote authorized scope (§7):** local restricts synthetic-quote generation to platform admins only; P0 additionally permits members of the demo RFQ's own buying organization. Concrete UI evidence (`EvaluationDecisionCockpit.tsx`'s existing "Demo: Simulate Quotes" button, gated only on a build-time `isDemoMode` flag, not on caller role) suggests the product's actual intent already assumes P0's broader scope, but this report does not decide the question — it surfaces the evidence and stops.

**A third, unanticipated finding emerged from function-body-level comparison and is arguably the most operationally important result of this task: P0's `apply_tds_withholding_atomic` has a verified, unconditional runtime defect** — its audit-event `INSERT` references columns (`action`) that do not exist on `audit_events`, with no exception handler, meaning **every call to this function under P0 as currently written would fail outright** (§4, §8). This is not a matter of interpretation or a product-policy question; it is a reproducible SQL-level bug, inherited unchanged from a pre-existing `origin/main` baseline, that local main's independent rewrite of the same function happens to fix as a side effect of doing a full rewrite for an unrelated reason (A-13's client-trust defect). A second, narrower instance of the identical column-mismatch defect exists in P0's `admin_bulk_delete_users` audit insert, silently swallowed by an exception handler there rather than raised.

**Substantial, non-overlapping local-main work exists that has no P0 counterpart whatsoever** and is not touched by, blocked by, or in conflict with anything in the P0 hotfix: the TDS taxable-base server-derivation and dedupe logic, the work-order milestone-sequencing trigger, the pilot-RFQ-allowance trigger, the buyer-address ownership check, the `rfqs` address-snapshot column-grant restriction (all bundled inside local `00199`), plus the entirety of `00200` and `00202`, plus two of three fixes each in `00201` and `00203`. None of this requires the P0/local reconciliation decision to be made first — it requires only that local main's `00199`–`00203` chain itself be executed and validated (A-R7), which has never happened.

**Eight hidden collisions were found** by exhaustive cross-referencing of every function/policy/trigger name touched by both chains (§8) — five are exact duplicates (harmless if de-duplicated), one is the genuine Conflict A fork, one is the genuine Conflict B fork, and one is the P0 audit-column defect surfacing a second time inside `apply_tds_withholding_atomic`.

**No reconciliation strategy is technically mandated by the evidence** (§12) — Options 1, 2, and 3 are all consistent with every fact gathered in this report; the choice among them is a release-engineering preference, not a finding this investigation can settle.

**Bottom line:** the collision is confirmed, its true scope is narrower than previously documented, exactly two product decisions are genuinely required (not the six-plus items the Phase-0 artifact implied were blocked), a concrete P0-side defect independent of any product decision was found and should be fixed regardless of which reconciliation option is chosen, and a large body of local-main work can proceed immediately without waiting for any of the above. 32FIX implementation is **not** ready to begin on the items this task re-examined until the two product decisions are made and local `00199`–`00203` is executed/validated at least once — but far fewer items are actually blocked than `32FIX_IMPLEMENTATION_ORDER.md` currently states.

## 6. Conflict A — `admin_bulk_delete_users`

**P0 version — hard delete, with a soft-delete option the caller can decline.** Body inherited unchanged from origin/main migration `00186` except for the authorization guard. `p_soft_delete boolean DEFAULT true`. When `p_soft_delete IS TRUE` (the default): sets `profiles.status = 'DELETED'`, `deleted_at = now()`, and marks matching `signup_requests` as `REJECTED` — a true soft delete. When `p_soft_delete IS FALSE`: performs a cascading **hard delete** — `DELETE FROM profile_roles`, `organization_members`, `supplier_users`, then (best-effort, exceptions swallowed) `notification_preferences`, `password_reset_otps`, then `signup_requests`, then `profiles` itself, then (best-effort) `auth.identities` and `auth.users`. The audit-event insert (`actor_id, actor_role, action, entity_type, entity_id, payload`) references two columns (`actor_role`, `action`) that do not exist on `audit_events`, and this insert is wrapped in its own `BEGIN...EXCEPTION WHEN OTHERS THEN NULL`, so on every call — soft or hard — the audit write **silently fails and no record is ever created**, while the function still returns `ok:true`.

**Local-main version — soft-delete only, hard-delete refused.** Same guard. `p_soft_delete` parameter is retained in the signature for compatibility but is **never honored as a hard-delete request** — every call, regardless of the flag's value, sets `profiles.status = 'DELETED'` and `deleted_at`, never deletes any row from any table, and the response includes `hardDeleteRefused: (p_soft_delete IS FALSE)` so a caller that asked for a hard delete is told, explicitly, that it did not get one. The audit-event insert uses the real `event_type` column and is not exception-wrapped, so a caller relying on the audit trail existing would find out immediately (via a hard function failure) if it ever broke, rather than silently losing the record.

- **Security implications:** Hard delete (P0) permanently destroys `auth.users`/`auth.identities` rows, which removes the account's ability to ever authenticate again through that identity — this can be a legitimate security response to a compromised or malicious account, but it also destroys the forensic trail for that account beyond whatever `audit_events` captured (and P0's own audit write for this action is broken, so in practice **no forensic trail survives a P0 hard delete at all**). Soft delete (local) preserves every row and every reference, which is safer for later investigation but means a "deleted" account's data (email, phone, org membership history) remains queryable in the database indefinitely — a data-minimization/right-to-erasure consideration if this system is ever subject to such requirements.
- **Referential-integrity implications:** Hard delete cascades through `profile_roles`, `organization_members`, `supplier_users` explicitly, and *attempts* `notification_preferences`/`password_reset_otps` (swallowing errors), but does **not** appear to touch `audit_events.actor_id`, `rfqs.created_by`, `quotes`, `invoices.created_by`-style foreign keys, or any other table that references `profiles.id` elsewhere in the schema (not enumerated in the function body) — a hard delete could leave dangling references or trigger FK-constraint violations depending on each table's `ON DELETE` behavior, which this task did not exhaustively enumerate (see §13). Soft delete has no referential-integrity risk since no row is removed.
- **Audit implications:** P0's version never successfully writes an audit event for this action (verified defect, §4). Local's version writes a correct one every time (or the call fails loudly if it can't).
- **User/account-recovery implications:** Hard-deleted accounts cannot be recovered — the person would need to re-register from scratch, losing all history. Soft-deleted accounts retain every row and could, in principle, be "undeleted" by an admin flipping `status` back (no such reverse RPC currently exists in either chain).
- **Existing UI assumptions:** `apps/web/src/features/admin/api/admin-ops.ts` and `AdminUsersActivityPanel.tsx` are the client callers (per `git show --stat` on commits `5325988`/`2dd3c2d`, both touch these files). This task did not trace whether the current UI ever passes `p_soft_delete = false` explicitly or always uses the default — that is a concrete, bounded follow-up (§13), not re-verified here.

## 7. Conflict B — Synthetic/Demo Quote Scope

**Local-main `00198` policy — platform admin (or backend role) only.** `private.assert_synthetic_quotes_allowed(p_rfq_id)`: returns a denial reason unless the caller is `private.is_platform_admin()`, `auth.role() = 'service_role'`, or `session_user IN ('postgres','supabase_admin')` — **organization membership of the caller is never checked**, and is irrelevant to the outcome. - **Pilot/simulator flags:** `otp.demo_staging`/`otp.demo_reset` session-local GUCs are checked identically in both (used by seed/reset scripts, not by interactive users).
