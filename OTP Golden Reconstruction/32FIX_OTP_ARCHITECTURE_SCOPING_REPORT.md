## 1. Executive summary

**D-21 and A-30 are the same underlying defect wearing two hats, and should be fixed as one joint server-side redesign, not two independent patches.** D-21 is "the transport is broken in production" (a relative `/waha/api/sendText` path that only exists in `vite.config.ts`'s dev/preview proxy, per `WHATSAPP_GATEWAY_SEND_PATH` in `outbound-dispatch.ts:12`). A-30 is "the payload that transport carries is itself a secret that shouldn't reach the browser at all" (`request_profile_verification_otp` returns `otp_code` in its JSON response, `00178_phase6_group2_edge_and_adapters.sql:137-139`). Fixing D-21 alone (e.g. just proxying `/waha` in production) would still leave A-30's OTP visible in the network tab. Fixing A-30 alone (stop returning `otp_code`) makes today's client-side WhatsApp dispatch **impossible** — the browser needs the code precisely because it is the one sending the WhatsApp message. The only design that closes both is: **one new server-side component that generates the OTP, stores it (hashed), sends it via a real messaging provider, and returns to the browser only `{ ok, maskedDestination }` — never the code and never a client-triggered send.** This is not a 5-minute patch: it requires picking a WhatsApp transport that actually works from a server context (WAHA is not currently one of the two supported server-side providers), and it touches three separate client call sites, not the one the root-cause matrix names.

**B-01 is the broader onboarding/notification defect that A-29 is a named sub-part of** — B-01 is "the whole registration→approval→first-login journey has no guaranteed external notice on any leg" (7 files: `signup.ts`, `BuyerRegisterForm.tsx`, `SupplierRegisterForm.tsx`, `registration-outcome.ts`, `SignInForm.tsx`, `AdminUsersActivityPanel.tsx`, `admin-ops.ts`). **A-29 is specifically the approval leg**: a shared, hard-coded default password (`'Welcome@OTP2026!'`) provisioned server-side in `admin_review_signup_request`, and a "welcome" notice that is a **browser-initiated, best-effort side-effect** of the admin clicking Approve — not a guaranteed part of the transaction. A-29 formally depends on B-01 and D-21 (per `32FIX_IMPLEMENTATION_ORDER.md` and the inventory's `dependencies` field), and B-01 itself depends on D-21 — so the practical order is **D-21/A-30 (transport + OTP secrecy) → B-01 (onboarding notice architecture) → A-29 (replace the shared password within that architecture)**. All four items share one root problem: **every "we told the applicant/user something" claim in this codebase is currently made true or false by the browser tab that happens to be open at the time**, not by the server.

## 2. D-21 + A-30 — joint scoping

### 2.1 Current-state grounding

**The three real call sites that hit the broken path** (only one of which is in D-21's own `affected_files` list):

| # | File | What it does | Uses |
|---|---|---|---|
| 1 | `apps/web/src/features/portal/api/signup.ts:176-208` (`sendVerificationCode`) | Registration-time phone verification. Calls RPC `request_profile_verification_otp`, then builds a WhatsApp text literally containing `rpcData.otp_code` and calls `dispatchWhatsAppText`. | `request_profile_verification_otp` (00178) |
| 2 | `apps/web/src/features/auth/lib/password-reset-dispatch.ts:22-58` (`requestWhatsAppPasswordReset`) | Password-reset code. Calls RPC `request_whatsapp_password_reset`, gets `res.otp_code` back, builds a WhatsApp text containing it, calls `dispatchWhatsAppText`. | `request_whatsapp_password_reset` (`00118_whatsapp_password_reset.sql:186-196`) |
| 3 | `apps/web/src/features/admin/components/AdminUsersActivityPanel.tsx:452-467` (`handleReview`) | Post-approval "welcome" WhatsApp, containing the plaintext temporary password from `admin_review_signup_request`'s response. | `sendWhatsAppNotification` → same `dispatchWhatsAppText` |
| 4 | `apps/web/src/features/profile/api/profile.ts:184-194` (`requestProfileCredentialOtp`) | Profile phone-linking OTP (separate RPC pair `request_profile_credential_otp` / `verify_and_update_profile_credential`, not named in the inventory but structurally identical). | `request_profile_credential_otp` |

All four route through `dispatchWhatsAppText` in `apps/web/src/features/notifications/lib/outbound-dispatch.ts:106-144`, which `fetch()`es `WHATSAPP_GATEWAY_SEND_PATH = '/waha/api/sendText'` (`outbound-dispatch.ts:12`) directly from the browser.

**Why it only works in dev/preview:** `apps/web/vite.config.ts:127-132` (dev `server.proxy`) and `:161-166` (preview `proxy`) rewrite `/waha/*` to `http://127.0.0.1:3008/*` — a local WAHA instance that exists only on a developer machine. **`vercel.json:42-46`** has exactly one rewrite rule, `"source": "/(.*)" → "destination": "/index.html"` — the SPA catch-all. In production there is no server listening on `/waha/*` at all; the catch-all serves `index.html`, so `dispatchWhatsAppText`'s `fetch()` gets a 200 HTML response with no JSON body, `res.json()` throws (`outbound-dispatch.ts:87-91`), and the call is recorded as... actually resolved as `providerMessageId: null` on a 200 status → `resolveNotificationStatus` returns `SUBMITTED` (not `FAILED`) per `notification-status.ts:145-151`. **This is the "2xx HTML reply could be misrecorded as SUBMITTED" risk the root-cause matrix flags for D-21** — in production, every WhatsApp OTP/password-reset/welcome send would silently report "Submitted, delivery not confirmed" while nothing was ever sent anywhere.

**Why WAHA can't simply be "moved server-side" as a drop-in:** `supabase/functions/_shared/messaging/providers/resolve.ts:37-73` defines exactly three provider IDs — `TWILIO`, `META`, `MOCK`. There is no `WAHA` provider implementation anywhere in `supabase/functions/_shared/messaging/`. WAHA (a self-hosted WhatsApp Web automation gateway, reverse-proxied to `127.0.0.1:3008` in dev) is architecturally outside the provider abstraction the one real server-side messaging pipeline (`messaging-outbound`) already uses. Moving dispatch server-side therefore is not just "same code, different host" — it is either (a) writing a new `WahaMessagingProvider` adapter and standing up WAHA somewhere Vercel/Supabase Edge Functions can reach it over HTTPS, or (b) switching these four call sites onto `TWILIO`/`META`, which are already integrated, tested (`_shared/messaging/providers/*.test.ts`), and used by `messaging-outbound` — but require real provider credentials that, per `R2-31-32-Issue-Root-Cause-Remediation-Report.md` section G, do not currently exist in any environment ("no credentials, no delivery webhooks wired").

**Why `messaging-outbound` can't be trivially reused as-is:** `supabase/functions/messaging-outbound/index.ts` is purpose-built for one thing — notifying an **invited supplier about an RFQ**. Its contract:
- Input: `{ rfqId, supplierId, invitationId }` (`:49-53`) — there is no `phone`/`text` parameter at all.
- It looks up the phone number itself from `supplier_messaging_channels` (`:100-105`), not from the caller.
- The message body is not caller-supplied; it is rendered by `renderRfqNotification` from `_shared/messaging/templates.ts`, which calls `assertPayloadIsSendable` (`templates.ts:76-88`) — a hard allow-list of ~14 RFQ-specific fields. Passing free-form OTP text through this function would throw `NotificationPolicyViolation` immediately.
- It is invoked "server-to-server only, by the `rfq_invitations` insert trigger via `pg_net`" (file header comment, `:11-14`) — not designed as a public-facing endpoint for arbitrary recipients.
- It writes its send record to `supplier_notifications` via RPC `record_supplier_notification`, a table scoped to suppliers, not to signup applicants or existing account-holders resetting a password.

None of this is a reason it *couldn't* be extended — it is well-factored and the provider/template split is exactly the right shape — but "reuse `messaging-outbound`" is not a same-day change: it needs a second template function outside the RFQ allow-list, a second caller contract (destination + body, not RFQ/supplier IDs), and a decision on whether OTP sends should log to `supplier_notifications` or a new/general notification-log table.

**A-30's specific defect, independent of transport:** `request_profile_verification_otp` (`00178_phase6_group2_edge_and_adapters.sql:109-145`) generates a 6-digit code with `lpad(floor(random() * 900000 + 100000)::int::text, 6, '0')` (`:127` — `random()`, not a CSPRNG, and a separate weakness from the one scoped here), stores it in `signup_verification_otps` **in plaintext** (`:100-105`, column `otp_code text NOT NULL`, no hash), and returns `'otp_code', v_otp_code` directly in its JSON response (`:137-139`), `GRANT`ed to `anon` (`:145`). **Any caller — not just the legitimate registration form — can call this RPC directly (e.g. via `curl` against the Supabase REST endpoint) and receive a real, usable OTP for any phone number in the request, with no proof any message was ever sent.** The identical pattern exists in `request_whatsapp_password_reset` (`00118_whatsapp_password_reset.sql:186-196`, table `password_reset_otps` at `:4-11`, also plaintext, also `anon`-granted) and in `request_profile_credential_otp` (referenced from `apps/web/src/features/profile/api/profile.ts:145-166`, not yet located in a numbered migration in this pass but structurally the same family). **All three OTP-issuing RPCs share this shape** and are candidates for the same fix, even though only one (`request_profile_verification_otp`) is named in A-30's `affected_rpc`.

**A-30's client call site is currently unreachable from the registration UI** — worth stating precisely because it changes the blast-radius picture. `sendVerificationCode` (`signup.ts:167`) is exported from `signup.ts` and re-exported from `apps/web/src/features/portal/index.ts:29`, but a repo-wide search finds no call site inside any React component (`BuyerRegisterForm.tsx`/`SupplierRegisterForm.tsx`/`VerificationChoice.tsx`/`SignupPage.tsx`) — only `signup.ts` itself and a test file reference it. `VerificationChoice.tsx` (`apps/web/src/features/portal/components/VerificationChoice.tsx`) only lets the applicant choose *how* they'd like their registration acknowledgement delivered (`verification_channel` stored on the `signup_requests` row) — it does not gate account creation on entering a code, and `verify_profile_verification_otp` (the matching verify RPC, `00178:147-184`) has **zero call sites anywhere in `apps/web/src`**. So today, the actual registration journey never exercises this OTP pair at all; **the vulnerability is real and independently exploitable via a direct RPC call (the function is `anon`-granted regardless of UI wiring), but it is not currently the thing a real applicant experiences.** Any fix must decide whether to (a) wire this dead pair into a real phone-verification step for the first time, (b) delete it as unused, or (c) fold it into the new joint OTP-delivery mechanism being built for D-21 anyway.

### 2.2 Design direction(s), with tradeoffs

Both directions below assume the core principle from R2-31 (item 30 / SEC-8) that the client must never see a raw OTP code again; they differ only in *what the browser is told after the send*.

**Direction A — one new edge function, `otp-dispatch`, that owns generation + storage + send.**
- New: `supabase/functions/otp-dispatch/index.ts`. Contract: `POST { purpose: 'SIGNUP_VERIFY' | 'PASSWORD_RESET' | 'PROFILE_CREDENTIAL', identifier }` → generates the code server-side (CSPRNG, e.g. `crypto.getRandomValues`), calls a new/extended messaging-provider send, stores only a hash (e.g. SHA-256 via WebCrypto, matching the pattern already used for `MessagingConfigError`-style provider selection) with an expiry, and returns `{ ok, maskedDestination: '+91••••••789', channel }`. Verification stays a Postgres RPC (`verify_*`) that hashes the caller-supplied code and compares.
- Reworks `request_profile_verification_otp`/`request_whatsapp_password_reset`/`request_profile_credential_otp` to no longer generate+return the code themselves; they either become internal-only (`SECURITY DEFINER`, called by the edge function with the service key) or are retired in favour of the edge function calling a single new `private.issue_and_send_otp(...)` helper directly.
- Pros: one place owns the "never leak the code" invariant for all three OTP families at once; naturally reuses whichever provider (Twilio/Meta) is configured, because it's the same provider abstraction `messaging-outbound` already uses; matches the "one new edge function" framing in the brief.
- Cons: new function to write, test, and deploy (config, secrets, CORS); three call sites' request/response shapes change, so `signup.ts`, `password-reset-dispatch.ts`, and `profile.ts` all need updating; the "is this actually reachable from the deployed frontend" question (Vercel → Supabase Edge Function CORS/URL) needs to be solved once, cleanly, rather than three times ad hoc.

**Direction B — keep the RPCs as the generator, add a second, narrowly-scoped edge function purely for "send whatever provider-safe text this RPC just committed to a table."**
- The Postgres RPCs keep generating/hashing/storing the OTP (as they do for the record already, minus returning the plaintext) and, in the same transaction, insert a row into a new `outbound_otp_queue` table with `{ destination, body, purpose }`. A very small edge function (`otp-relay`) is invoked immediately after (client calls it right after the RPC, passing only the row id — never the code) or via a `pg_net` trigger (matching the existing `rfq_invitations` → `messaging-outbound` pattern) and does nothing but "read the queued row, call the provider, mark sent."
- Pros: mirrors the already-proven `messaging-outbound` trigger pattern exactly (lowest architectural novelty); keeps "what text do we send" decisions in SQL next to the data, consistent with how `supplier_rfq_message_payload` works today.
- Cons: two moving parts instead of one; a `pg_net`-triggered design means the client gets no immediate confirmation of provider acceptance in the same request/response cycle it does today (UX regression unless the client polls or the RPC call itself blocks — which reintroduces synchronous coupling); needs a new table plus RLS for the queue.

**Either direction requires a WAHA-vs-Twilio/Meta decision (Decision 1, below) before implementation, because the two supported server-side providers (Twilio, Meta) need real credentials that per R2-31 do not yet exist, while WAHA has none of the reliability the codebase already assumes elsewhere ("provider callback" delivery statuses, webhook signature verification) and is not represented in the `MessagingProviderId` type at all.**

## 3. B-01 — scoping

### 3.1 What B-01 actually is (per the inventory's own text, `32FIX_REMEDIATION_INVENTORY.json:1067-1096`)

> "Registration only writes a PENDING `signup_requests` row (no auth account/profile); acknowledgement is WhatsApp-only from the browser, so EMAIL-channel applicants get nothing. On approval the server provisions `auth.users` with a shared default password (`'Welcome@OTP2026!'`) and only an in-app notification the applicant cannot see; the real external notice depends on the approving admin's own browser calling `resetPasswordForEmail`/WAHA WhatsApp, which is unreachable on Vercel (D-21). Bulk 'approve all' sends nothing, and production still shows pre-fix success copy."

This is **not one bug** — it's a statement that *no leg of the onboarding journey has a guaranteed, server-owned external notice*:

1. **Submission** (`submit_signup_request`, `00035_signup_requests.sql:119-193`): writes the row; only ever tells the applicant a `reference` + `status: 'PENDING'`. Grounded: confirmed current behaviour, and also confirmed `already_submitted: true` is returned when a duplicate exists (`:154-157`) — a live instance of the *separate* D-26 enumeration issue, not this report's concern but visible in the same function.
2. **Registration acknowledgement**: `BuyerRegisterForm.tsx:154-160` (and the equivalent in `SupplierRegisterForm.tsx`) calls `sendWhatsAppNotification` **directly from the browser** only `if (channel === 'WHATSAPP' && phone.trim() && !result.result.alreadySubmitted)` — an EMAIL-channel applicant gets nothing at all beyond the on-screen `RegistrationOutcome` copy (`registration-outcome.ts`), and even the WhatsApp branch is subject to D-21's broken transport.
3. **Approval** (`admin_review_signup_request`, `00161_fix_admin_review_signup_request_robustness.sql:22-461`): provisions `auth.users` with `p_initial_password text DEFAULT 'Welcome@OTP2026!'` (`:27`), writes an **in-app** `create_system_notification` row (`:417-425`) the applicant — who has no session yet — cannot see, and returns `'temporary_password', p_initial_password` (`:451`) to the calling admin's browser. The *only* external notice is what `AdminUsersActivityPanel.handleReview` (`:440-468`) chooses to do next: call `supabase.auth.resetPasswordForEmail` and `sendWhatsAppNotification` from the admin's own browser, wrapped in individual `try/catch` blocks that turn any failure into a logged status string, never a hard error.
4. **Bulk approval** (`handleApproveAllPending`, `AdminUsersActivityPanel.tsx:584-602`): confirmed to call only `reviewSignupRequest(req.id, 'APPROVE')` in a loop — **no** email/WhatsApp call at all. An applicant approved via "Approve All" gets the shared password provisioned server-side and literally no notice of any kind, ever, from any channel, unless they happen to already know to try logging in.
5. **First login** (`SignInForm.tsx`): out of scope of files read in this pass beyond the inventory's citation (`:788-790`); the risk named is that first sign-in relies on the applicant somehow knowing the shared default password.

### 3.2 Design direction

B-01's fix is not "add a notification" — it is "give the onboarding pipeline exactly one place where an external notice is a guaranteed side effect of a state transition, for every transition, on every channel, whether triggered by one admin click or a bulk action." Concretely, this converges with D-21/A-30's joint redesign in one specific way: **the same new server-side dispatch primitive built for OTP delivery is the right place to also fire "registration received" and "approved — set your password" notices**, because both need "generate content server-side → send via a real provider → record a truthful delivery status" and neither should depend on which admin/applicant browser tab is open.

Two sub-decisions specific to B-01 (beyond the OTP-transport ones already listed under D-21/A-30):
- **Provisioning without a password at all** (invite/magic-link/set-password-on-first-login), which the inventory's own `surgical_fix` field recommends ("Replace shared default password with an invite/magic-link/set-password flow") — this is exactly A-29's job; B-01 is the pipe the notice travels through, A-29 is what the notice says and how the account first gets a password.
- **Where the "registration received" acknowledgement fires from**: at submission time (inside `submit_signup_request`'s transaction, via the same `pg_net`-trigger pattern `rfq_invitations` uses for `messaging-outbound`) rather than as a second client call after the RPC returns (today's `BuyerRegisterForm.tsx:154-160` pattern). Triggering server-side removes the "EMAIL channel gets literally nothing" gap for free, since the trigger doesn't care which channel the applicant is chatting to a browser over.

## 4. A-29 — scoping

### 4.1 Current-state grounding

A-29's root cause is fully inside `admin_review_signup_request` (`00161_fix_admin_review_signup_request_robustness.sql`):
- `p_initial_password text DEFAULT 'Welcome@OTP2026!'` — the function signature itself (`:27`).
- That literal password is what's actually written to `auth.users.encrypted_password` via `extensions.crypt(p_initial_password, extensions.gen_salt('bf'))` (`:149`) whenever a brand-new `auth.users` row is provisioned (i.e., every first-time approval where the email wasn't already an existing user, `:130-190`).
- It is returned to the caller verbatim: `'temporary_password', p_initial_password` (`:451`).
- The client (`admin-ops.ts:1122`, and the default parameter threaded through `AdminUsersActivityPanel.tsx`) also defaults to the exact same literal `'Welcome@OTP2026!'` — so even if an admin never customises it, **every single first-time approval across the whole platform provisions the identical password** unless the admin manually types a different one per-approval (there is no UI for that shown in the excerpts read; `reviewSignupRequest(request.id, action)` in `handleReview` — `:436` — calls with no `notes`/`initialPassword` override, so it always takes the RPC's own default).
- The compatibility alias `review_signup_request` (`:463-475`) carries the same default.

**Why 00199 (unexecuted) doesn't fix this even once applied:** `00199_harden_privileged_rpcs_supplier_masking_and_financial_enforcement.sql`'s guard-sweep (`:44-100+`) is a generic, mechanical strip of "always-true admin-check disjuncts" applied to a list of function names including `admin_review_signup_request` (`:74`). It fixes *who may call the function*, not *what the function does once called* — the shared-password body logic is untouched by that migration. A-29 needs its own, separate fix regardless of whether/how the 00199 conflict (see `32FIX_IMPLEMENTATION_ORDER.md` Conflict Map) is resolved.

### 4.2 Design direction

The inventory's own `surgical_fix` text is the right shape: **replace the shared default password with an invite/magic-link/set-password flow.** Concretely, this looks like reusing the pattern that already exists for a *different* actor in this codebase — `supabase/functions/supplier-magic-link/index.ts` issues a short-lived, single-use, capability-scoped token via `redeem_supplier_magic_link`, explicitly designed so "two people opening the same forwarded link cannot both get in." The same shape (a single-use, expiring, hashed token stored server-side, redeemed once to set a real password / establish a session) is the natural template for A-29, rather than inventing a new pattern.

Concretely, `admin_review_signup_request` would stop taking/writing a `p_initial_password` at all; on first-time provisioning it would either (a) create the `auth.users` row with a random unusable password and immediately issue a Supabase `resetPasswordForEmail`-style recovery link server-side (removing the need for the admin's browser to separately call `resetPasswordForEmail`, which is exactly what `AdminUsersActivityPanel.tsx:441-450` does today as a *second*, independent, best-effort step), or (b) mint a new "first login" token analogous to the supplier magic link, redeemed by a new page (`/activate?token=...`) that sets the real password. Both close the "one password works for every new account" hole; they differ in whether they reuse Supabase Auth's own recovery-email plumbing (simpler, but email-only — WhatsApp-channel applicants are back to the D-21/B-01 problem of getting the link to them) or build a bespoke token (more work, but channel-agnostic, matching the "OTP delivered exclusively via the out-of-band channel" principle A-30 is being fixed to uphold).

### 4.3 Blast radius

- `admin_review_signup_request` (`00161`, superseded by a new migration): signature change (drop `p_initial_password`), body change (no `extensions.crypt(p_initial_password, ...)` on first provisioning), response shape change (no `temporary_password` field — or replaced with a token/link reference).
- `review_signup_request` alias (`00161:463-475`) — same signature change, since it just delegates.
- `apps/web/src/features/admin/api/admin-ops.ts` — `reviewSignupRequest`'s `initialPassword` parameter (`:1119-1122`) and the `AdminReviewSignupResponse` type (not read in this pass; needs updating wherever `temporary_password` is typed).
- `apps/web/src/features/admin/components/AdminUsersActivityPanel.tsx` — `handleReview`'s credential-line construction (`:453-456`, which branches on `res.temporary_password` today) and the client-side `resetPasswordForEmail` call (`:441-450`), both of which become dead code if the server now handles first-credential issuance itself.
- Every existing `auth.users` row already provisioned with the literal `'Welcome@OTP2026!'` password (an unknown, unquantified number, since this is a live-database question this local-only pass cannot answer) is a **residual credential-reuse risk that a code fix alone does not remediate** — see Decision 5.

## 5. PRODUCT DECISION REQUIRED

The following are genuine product/behavioural choices, not engineering implementation details. Each is phrased so it can be relayed to a human decision-maker as-is; no option is recommended over another.

1. **WhatsApp transport for server-side OTP/notification delivery (blocks D-21, A-30, B-01, A-29):** Should the platform (a) **keep WAHA** and build a new self-hosted-WAHA server-side adapter (requires standing up WAHA somewhere reachable over HTTPS from Supabase Edge Functions/Vercel, and writing a `WahaMessagingProvider` matching the existing `MessagingProvider` interface), or (b) **switch to Twilio and/or Meta WhatsApp Business API** — already integrated and tested in `_shared/messaging/providers/`, but requiring real provider accounts/credentials that do not currently exist in any environment per prior findings, or (c) **support both**, with a configurable primary/fallback? Tradeoffs: (a) preserves whatever cost/behaviour assumptions WAHA was originally chosen for (e.g. using a real WhatsApp number without per-message provider fees) but WAHA's reliability/ToS-compliance for business messaging is unautomated and self-hosted-fragile; (b) is more standard/supported and immediately reuses tested code, but has real per-message cost and a signup/verification lead time for provider accounts; (c) is the most resilient but the most engineering effort.

2. **Should OTP delivery failures fail open or fail closed for registration/verification (blocks D-21/A-30, and touches B-01's "EMAIL-only applicant gets nothing" gap)?** If the chosen WhatsApp/SMS provider is unreachable or misconfigured, should the applicant (a) be **blocked entirely** from that verification step until a channel works, or (b) be **automatically offered/fallen-back to email** (Supabase Auth's existing `signInWithOtp`/email flow, already present in `signup.ts:210-221`) with a clear "WhatsApp is unavailable right now" message, or (c) be allowed to **proceed without verification** in some reduced-trust state pending manual review? Tradeoffs: (a) is safest but can strand real applicants during a provider outage; (b) matches the existing `VerificationChoice` UI's intent (WhatsApp offered first, email as an alternative) but doubles the number of channels that must be kept truthful; (c) unblocks growth but weakens the verification guarantee the whole redesign exists to strengthen.

3. **Should the demo-build "show the OTP on screen" behaviour survive the redesign?** `apps/web/src/features/profile/api/profile.ts:169,198` currently shows the real OTP code on screen whenever `VITE_DEMO_MODE === 'true'`, specifically so a demo/pilot environment without real WhatsApp/email credentials remains testable end-to-end. Should the new server-side-only design (a) **keep an explicit demo-mode escape hatch** (the server returns the code only when a server-side env flag, not a client-side build flag, says it's a demo/test environment — closing the "client build flag controls a security property" gap that exists today), (b) **remove the escape hatch entirely** and require a real provider (even a `MOCK` provider that "delivers" to a visible test inbox/log) for any environment including demos, or (c) **keep today's client-flag behaviour unchanged** because pilot/demo needs are judged more urgent than the residual risk? Tradeoffs: (a) is the most secure but means demo/pilot environments need their own credentials or a mock provider wired end-to-end before this ships; (b) forces that work immediately; (c) accepts that anyone who can flip a client-side env var locally (or inspect a demo build) can still see OTPs, which is the exact class of issue A-30 exists to close, just scoped to demo builds.

4. **Should the currently-dead registration-time phone-verification flow (`request_profile_verification_otp` / `verify_profile_verification_otp`) be revived as a real gate, or retired?** Confirmed: no UI component currently calls `sendVerificationCode` or exercises `verify_profile_verification_otp`; a real applicant today is never asked to enter a code before their `signup_requests` row is created. Should the redesign (a) **wire this up for the first time** as a genuine "prove you own this phone number before we accept your registration" step (a meaningful trust improvement, but new UX/QA surface, and a decision on whether registration should now block on it), (b) **delete the unused RPC pair and client function** as dead code and rely solely on the post-approval notice being trustworthy, or (c) **leave it exactly as-is** (unused in the UI, but still fixed at the RPC level so a direct API call no longer leaks a usable code)? Tradeoffs: (a) closes a real trust gap but is scope growth beyond "fix the leak"; (b) is the smallest change but discards work that already exists; (c) fixes A-30's literal defect (no code returned to any caller) with the least behavioural change, but leaves a fully-built, unused verification feature sitting in the codebase indefinitely.

5. **What should happen to `auth.users` accounts already provisioned with the shared literal password `'Welcome@OTP2026!'` (blocks A-29's rollout, not its code change)?** Should the platform (a) **force a password reset on next login** for every account that still has this password (requires a way to mark/detect them — e.g. a flag set at provisioning time going forward, but retroactively unknown for anything already provisioned before that flag existed), (b) **do nothing retroactively** and only prevent *new* shared-password provisioning, accepting that any already-provisioned account remains crackable by anyone who read this password in a repo, a report, or a chat log, or (c) **proactively rotate** every such account's password server-side and notify the holder via whatever new guaranteed-delivery channel B-01 builds? This is a genuine live-data/security-incident-response question this local-only pass cannot answer (the actual count and identity of affected accounts is a production-database question), not an engineering choice.

6. **Should bulk "Approve All Pending" (`AdminUsersActivityPanel.handleApproveAllPending`) get the same guaranteed external notice as single approval, and if so, synchronously or queued?** Confirmed: today, bulk-approving N pending requests sends zero notices of any kind for any of them. Should the fix (a) make bulk-approve **send N individual notices synchronously** in the same admin action (simplest, but means one slow/failing provider call blocks or partially fails a batch, and the admin's browser session must stay open for the whole batch), (b) **queue N notices** for a background/trigger-driven process to work through (more resilient, but reintroduces "was it actually sent" lag the whole redesign is trying to make honest), or (c) **require single-item approval only** and remove the bulk-approve button, forcing an admin to review and approve applicants one at a time so each gets an individually-confirmed notice? Tradeoffs are between operational throughput for the platform admin versus the guarantee-strength the rest of this redesign is built around.

7. **What should the client be told after a successful OTP-delivery request, precisely?** The brief specifies "only a success/failure + masked-destination indicator" — but should "masked" mean (a) a **partially-redacted phone number** (e.g. `+91••••••789`), which confirms to the requester which number will receive it (useful if the applicant has multiple numbers on file and needs to confirm which one), or (b) **no destination detail at all**, just `{ ok: true }` (marginally more private, but means a genuine typo in the phone number produces the same response as success, which is worse UX and makes the applicant's own error harder to catch before they wait for a code that will never arrive)? This is a small-seeming but real product tradeoff between confirmability and information minimisation.

8. **For A-29's replacement flow, should the "set your password" step be Supabase Auth's built-in email-recovery link, or a bespoke channel-agnostic token?** Restated from §4.2 as its own decision because it has real cost implications: (a) **Supabase's own `resetPasswordForEmail`** is already wired, tested, and used elsewhere in this codebase (`AdminUsersActivityPanel.tsx:441-450`, `password-reset-dispatch.ts`), but is email-only — a WhatsApp-only applicant (no email delivery path chosen) is left with no way to receive it unless email is always sent regardless of their stated channel preference; (b) a **bespoke single-use token** (mirroring `supplier-magic-link`) can be delivered over whichever channel the applicant actually verified, but is new code to build, test, and secure (token entropy, expiry, single-use enforcement) essentially from scratch for this one flow, in parallel with the OTP-delivery mechanism being built for D-21/A-30.
