Cleanup references establish only that scripts expected an object by that name. Admin deletion filtered on `id`, which is not a schema contract. No database was queried.

**Classification: D — unresolved reference; `NOT VERIFIED — EXTERNAL/SCHEMA EVIDENCE REQUIRED`.** Static evidence cannot establish whether the table exists in an external schema, is an obsolete object, or was provisioned outside tracked migrations. No tracked application feature uses it; no generated `requirement_specifications` table type, defining DDL, or RLS/grant contract was found. The generated schema does include `requirements` and its `structured_specs` JSON column.

`requirements.structured_specs` is the current compatibility representation, maintained as a legacy JSON mirror by migration `00014`; typed requirement columns and `attributes` are primary for current intake. Clarification code optionally reads JSON `line_items`/`items`, but no tracked item persistence contract was found. It therefore is not evidence that a normalized buyer-side item lifecycle already exists.

## Reuse conclusion
Reuse `requirements` as independently publishable children and existing `rfqs`/protected publication lifecycle. The unique `rfqs.requirement_id` relationship supports one RFQ per child without a parallel RFQ system. A parent orchestration record is justified because no tracked group exists and the exact mixed original description must remain buyer-only. The buyer-item storage choice is **BLOCKED**: inspect authoritative `requirement_specifications` schema/API before deciding to extend it or add an item model.

- **Decision:** retain the prior frozen rule: each independently reviewable child is one single-category scope and its own RFQ; parent is coordination only.
